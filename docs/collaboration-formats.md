# 共同作業と書式登録

各自のPCで`AIWorkspace.exe`を起動し、そのPCのブラウザから操作します。AIの実行、LLM設定、資格情報は各PCで管理し、文書・コード・タスク・共有進捗はGitHubで共有します。専用の共有ホストは必要ありません。

## 開発前に書式を登録する

1. 「接続・環境設定」でGitHubリポジトリと自分のトークンを設定します。リポジトリには基準ブランチを用意してください。
2. プロジェクトを作成し、開発手法、目的、基準ブランチ、リーダーのGitHubユーザー名を指定します。
3. 「個人テンプレート」で書式候補を用意します。Markdown本文を直接編集するか、`.md`をアップロードし、文書種別、必須見出し、表の列を設定します。
4. 「開発準備・書式登録」で必要な文書種別ごとに書式を選択します。プレビューを確認し、「書式登録PRを作成」を実行します。
5. GitHubで登録PRの内容を確認してマージします。一人開発では自分をリーダーに指定し、自分で作成したPRをマージできます。GitHubの自己Approveは不要です。
6. ブラウザへ戻り、「承認・マージを確認」を実行します。「開発準備完了」と固定コミットが表示されたら、「GitHubと同期」で他の参加者へ設定を共有します。
7. 「対話・タスク」で「担当を取得」してから「AIで作成」を実行します。

書式登録PRの作成だけでは開発を開始できません。GitHubでマージ済みであれば、作者・マージ実行者・レビューの有無にかかわらず「承認・マージを確認」で通過します。PRの対象版が変更された場合、指定した基準ブランチやリポジトリと異なる場合、書式の内容が登録時のハッシュと一致しない場合は準備完了になりません。未マージのまま閉じただけのPRは通過しません。

## 個人書式とプロジェクト書式

| 書式 | 保存先・共有方法 | 編集した場合 |
|---|---|---|
| 個人テンプレート | 各PC内。書式の候補として使う | そのPCの候補だけを変更 |
| プロジェクト書式 | 選択した書式をPRでGitHubへ登録 | 変更時は新しい登録PRと承認・マージが必要 |
| プロジェクト書式のキャッシュ | 各PC内の個人書式とは別の領域 | GitHubの固定版とハッシュを検証して取得 |
| 生成済み成果物の書式 | 成果物に使用時の本文・ハッシュを保存 | 後から書式を変えても既存成果物は変更されない |

同じIDの個人テンプレートが参加者のPCにあっても、GitHubから取り込んだ書式で上書きしません。別案件の個人テンプレートを一括でGitHubへ送る処理も行いません。GitHubへ共有される書式は「開発準備・書式登録」で選択してPRへ登録したものです。

書式登録PRには、Markdown本文、必須見出し・表などの定義、文書種別との対応表を含めます。マージ後は、そのマージコミットと各書式のハッシュを固定します。新しい参加者のPCでも、GitHubの承認と固定版の内容を検証してから使用します。共有データに「準備完了」と書かれているだけでは、検証を省略しません。

共有書式を変更する場合は、実行中のタスクを停止してから「開発準備・書式登録」で選び直し、新しいPRを作成します。リーダーの再承認・マージ確認後に、新たに生成する文書へ適用します。追加タスクが新しい文書種別を必要とする場合も、その書式を登録してから開始します。

## 他のPCから参加する

作成者は「工程・進捗」に表示される共有プロジェクトIDを参加者へ伝えます。参加者は自分のPCでexeを起動し、自分のGitHub認証を設定して「GitHubから参加」で同じリポジトリとプロジェクトIDを入力します。「共有プロジェクトを検索」から選ぶこともできます。

参加後は「開発準備・書式登録」で「承認・マージを確認」を実行し、同じ固定版の書式を取得してください。プロジェクト側で書式を変更した場合も、同期後に新しい登録内容を確認します。

このPCで行った操作やAIタスクの状態変化はSSEでブラウザへ随時反映します。他PCの進捗はGitHubへ同期された内容を、通常30秒間隔で取得します。必要なときは「GitHubと同期」を実行してください。GitHubのAPI制限や通信障害がある場合は反映が遅れます。別PCで生成中の文章や詳細ログをリアルタイム配信する仕組みではありません。

PCを終了すると、そのPCで実行中のAIは停止します。他のPCのタスクは継続できます。別PCの起動・再起動によって、自分の実行中タスクを中断状態へ変更しません。

## GitHub上で管理するデータ

共有状態はschema version 2を使用します。プロジェクト全体を1つのJSONファイルへ上書きする方式から、レコードごとの更新へ変更しています。

| ブランチ | 内容 |
|---|---|
| `ai-system/<project-id>` | `.ai-dev/project.json`にプロジェクト設定と書式登録情報を保存 |
| `ai-data/<project-id>/<kind>/<record-id>` | `.ai-dev/record.json`にタスク、成果物、対話、テスト記録を個別保存 |
| `ai-control/<task-id>` | `.ai-dev/owner.json`に担当ユーザー、端末、実行識別子を保存 |
| `ai-work/<task-id>` | 文書・コード・レビュー依頼などの成果物をPRで公開 |
| `ai-formats/<project-id>/<registration-id>` | プロジェクト書式を登録するPR |

変更したレコードだけを送信し、GitHubのファイルSHAが想定した版と一致することを確認して更新します。この比較付き更新をCASと呼びます。異なるタスクの状態更新が、共通の進捗ファイルを奪い合うことはありません。通信結果が不明になった場合も、保存済み内容を読み直し、同一内容なら成功として扱います。

複数レコードの更新は一括トランザクションではありません。途中まで成功した場合は、再同期時に公開済み内容を確認し、未完了の更新を再試行します。同じレコードに別内容の変更が見つかったときは、上書きせずローカルの変更を保持して停止します。

## 担当取得と引継ぎ

「担当を取得」はタスクごとの所有権ブランチを作成して担当を確定します。担当者・端末・実行識別子を確認し、別PCのタスク状態変更や、引継ぎ前の所有者からの共有更新・成果物公開を拒否します。担当情報は成果物ブランチと分離しているため、新しいPRへ所有者ファイルを追加しません。

引継ぎは、担当者が実行中の作業を停止し、必要な変更を同期してから行ってください。「引継ぎ」で相手のGitHubユーザー名と端末IDを指定します。担当者またはリーダーが操作できます。所有権の変更と引継ぎ直後の状態は確認済みの内容に限って共有し、その後の更新は新しい担当PCで行います。

引継ぎ先に未同期の変更がある場合、同じレコードの変更として競合することがあります。その場合もローカルの変更を保持します。どちらを採用するか確認して統合してください。競合を画面上で手動統合する専用UIは未実装です。

## 成果物とテストの対応を確認する

検証タスクは、依存する実装タスクの承認済み成果物を使います。成果物を検証用ディレクトリへ復元してから、AIによる読み取り・検索や登録コマンドによるテストを実行します。別PCにしか存在しない元の作業ディレクトリへ依存しません。

テスト記録には、対象成果物のID、ファイルごとのハッシュ、対象全体のハッシュ、実行したコマンド、結果を保存します。同じコマンドの最新結果が成功し、その対象ハッシュが現在の成果物と一致する必要があります。最新テストが失敗している場合に、過去の成功だけを選んで自動承認しません。実装の変更後は再テストが必要です。テストで対象ファイルを変更した場合や、unittestでテストが検出されなかった場合も成功として扱いません。

人による手動検証を採用する場合は、検証内容をコメントに記録してください。文書の見出し・表の機械検証やテスト結果だけでは、内容の正しさまでは保証できないため、生成された成果物のレビューも必要です。

工程の最後は「最終レビューPR作成」を実行し、GitHubで対象版を確認してマージするか、作者とは別の指定リーダーがApproveします。PR作者がリーダー本人の場合は、GitHubでマージしてから「承認・マージを確認」を押してください。マージ済みならレビューやCIをアプリ側で再条件化しません。未マージなら従来どおり指定リーダーの有効なApprove、未解消の変更要求がないこと、CI・マージ条件を確認します。GitHub側で必須レビューを設定している場合は、そのルールを満たす必要があります。

確認ではレビューとマージを区別し、マージコミット・実行者・日時を証跡として各PCに保存します。確認のたびに共有タスクを書き換えません。ブラウザの通常承認やIssueを閉じる操作だけでは最終承認になりません。

## 防げる競合と、残る競合

この構成で、共通の進捗ファイル、所有者ファイル、個人書式の一括同期が原因だった競合や上書きを防ぎます。

同じソースの同じ箇所を別内容で変更した場合や、同じ共有レコードを複数PCで別内容に変更した場合の競合は残ります。タスクの担当ファイルを分け、重なる作業は順番に実行し、PRで変更を確認・統合してください。GitHubを使うだけで、すべての競合が自動的に解消される仕組みではありません。

## 旧版から移行する

1. 実行中のタスクを停止し、各PCの未同期変更と公開済みPRを確認します。旧版のアプリは終了します。
2. 参加者全員を新版へ更新します。旧版と新版を同じプロジェクトで同時に使わないでください。
3. 新版で同期します。旧`ai-system/<project-id>`ブランチの`.ai-dev/shared.json`は読み取り専用の移行元として参照します。次の共有更新から、レコードごとの新形式へ保存します。
4. 「開発準備・書式登録」で共有する書式を選び、登録PRの承認・マージを確認します。旧`shared.json`内の個人テンプレートは取り込まず、各PCの個人書式を上書きしません。
5. 既存の作業ブランチ・PRを確認します。旧方式で既に追加された`.ai-dev/owner.json`は自動削除しません。PRに残っている場合は、成果物の差分を確認したうえで通常のGitHubレビューで除外・整理してください。

旧`shared.json`は履歴として残り、以前に保存された個人テンプレートをGitHubの過去履歴から削除する処理は行いません。新形式への移行後に、旧版から`shared.json`へ書いた変更は新形式のデータへ反映されないため、全員の更新が必要です。

実際に確認した試験の範囲と残る検証項目は、[テスト報告](test-report.md)を参照してください。
