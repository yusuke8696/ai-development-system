# AI Development Workspace

各自のWindows PCでexeを起動し、ブラウザからAIと対話して開発を進めるシステムです。

専用の共有サーバーは不要です。各PCでAIを実行し、GitHubでタスク・成果物・進捗を共有します。

## 起動

配布ZIPを展開し、`AIWorkspace/AIWorkspace.exe` を実行します。`_internal` フォルダーを含めて配置してください。ブラウザが開きます。exe自身の起動に外部Pythonは不要です。

初期設定:

1. 「接続・環境設定」でGitHubリポジトリと自分のアクセストークンを設定します。GitHubで事前にリポジトリと基準ブランチを用意してください。
2. 「LLMモデル」で接続テストを行います。初期値は `http://127.0.0.1:8080/v1`、モデルID `qwythos-9B-v2` です。
3. プロジェクトを作成し、開発手法・目的・リーダーのGitHubユーザー名を指定します。
4. 「OSSライセンス」で許可するライセンスをチェックし、必要ならSPDX IDと表示名を手入力で追加してON/OFFを選び、保存します。
5. 「個人テンプレート」で必要なMarkdown書式を用意し、「開発準備・書式登録」で文書種別ごとに選択して「書式登録PRを作成」を実行します。許可リスト・必須skill・osv-scanner用スクリプト・GitHub Actionsも同じPRへ登録します。
6. GitHubで登録PRの内容を確認してマージします。一人開発では自分をリーダーに指定し、自分のPRをマージできます。「承認・マージを確認」で固定版が登録されるまで、AIタスクは開始できません。
7. 「GitHubと同期」で共有し、タスクの「担当を取得」から「AIで作成」を実行します。AIの質問に回答して再開し、文書の原文・検証結果を確認して次へ進めます。
8. 「GitHubへ公開」で成果物のタスク別PRを作成します。通常の操作はブラウザUIで行えます。
9. 最後に「最終レビューPR作成」を実行し、GitHubでマージするか、PR作者とは別の指定リーダーがApproveします。「承認・マージを確認」または定期同期で、対象版とGitHubの状態を確認します。

終了は画面右上の「終了」を使います。ブラウザを閉じただけではexeは停止しません。通常の保存先は `%LOCALAPPDATA%/AIWorkspace/` です。資格情報はWindows DPAPIで暗号化してこのPC・ユーザーに紐付けて保存し、GitHubへ送信しません。

指定されたLLMの起動例（本アプリからモデルを自動ダウンロードしません）:

```powershell
llama-server -hf empero-ai/Qwythos-9B-v2-GGUF:Q4_K_M --host 127.0.0.1 --port 8080 -ngl 99 -c 16384 -n 8192 --jinja -fa on --verbose --alias qwythos-9B-v2
```

## GitHub設定と共同作業

接続テストが失敗した場合は、「接続・環境設定」の下部にある「GitHub接続診断」を確認してください。保存済み設定・トークン読込・通信初期化・GitHub認証・リポジトリ参照・既定ブランチ参照の結果と、HTTPステータス、対処方法を表示します。「診断結果のJSONを表示」から共有用の結果も確認できます。トークンや通信ヘッダーは含めません。v0.2.1の配布不具合による「復号できない」表示はv0.2.2で修正しました。詳しくは[接続診断ガイド](docs/github-connection-diagnostics.md)を参照してください。

初期版はGitHub.comに対応します。Fine-grained PATは対象リポジトリに限定し、Contents・Issues・Pull requestsのRead/Write、Checks・Commit statusesのReadを設定します。組織側の承認・SSOが必要な場合はその設定にも従ってください。トークンをURLや文書へ記載しないでください。

作成者は共有プロジェクトIDを他の参加者へ伝えます。IDは進捗画面に表示されます。参加画面の「共有プロジェクトを検索」でも取得できます。参加者は自分のPCでexeを起動し、「GitHubから参加」で同じリポジトリとIDを入力します。

- `ai-system/<project-id>`: プロジェクト設定と承認済み書式への参照。
- `ai-data/<project-id>/<kind>/<record-id>`: タスク・成果物・対話・検証記録をレコードごとに分離した共有状態。
- `ai-control/<task-id>`: 担当ユーザー・端末・実行識別子。成果物PRから分離します。
- `ai-work/<task-id>`: 基準ブランチから作成する成果物用ブランチ。
- `ai-formats/<project-id>/<registration-id>`: プロジェクトの書式登録PR用ブランチ。
- Issues: タスクと最終レビュー依頼。Issueを閉じるだけでは承認になりません。
- PR: 文書・コード・最終完了報告のレビュー。

共有状態はschema version 2を使用し、変更したレコードだけをGitHubのファイルSHAで確認して更新します。同じ共有ファイルを全員が書き換える方式を廃止し、独立したタスクの更新が競合しにくい構成にしています。別のPCが所有するタスクの状態変更や、引継ぎ前の所有者からの更新は拒否します。

「タスクを追加」で先行タスクと役割を指定すると、独立したタスクを複数人で並行して進められます。このPC内の変更はSSEで画面へ随時反映し、他PCの進捗は通常30秒間隔でGitHubから取得します。API制限時は遅れる場合があります。各PCの詳細ログやLLMの生成途中の文字列は共有しません。

同じソースの同じ箇所を変更した場合や、同じ共有レコードを別内容で更新した場合の競合は残ります。競合時は上書きせず、ローカルの変更を保持して停止します。担当範囲を分け、重なる変更はPRで確認・統合してください。

一人でも開発できます。リーダーに自分のGitHubユーザー名を指定し、PRの内容を確認してGitHubでマージしてください。GitHubではPR作者自身のApproveはできませんが、本システムではマージを承認の証跡として扱います。マージ済みのPRは作者・実行者・レビューの有無にかかわらず確認を通過します。書式の対象版・リポジトリ・内容ハッシュ、最終レビューの対象成果物の版は引き続き検証します。

未マージの最終レビューPRは、作者とは別の指定リーダーによる対象版へのApprove、未解消の変更要求がないこと、CIとGitHubのマージ条件が必要です。マージ済みならGitHubの決定を採用し、アプリ側でCI・レビューを再条件化しません。リポジトリの必須レビュー設定はGitHub側で適用されるため、一人開発の運用に合わせて設定してください。アプリからApproveやマージを自動実行する機能ではありません。アジャイルの各反復、AI-DLCの各サイクルの承認後、継続は「次の反復・サイクル」、全体を終了するときは「全体の最終承認へ」を選びます。

## 文書の書式

「個人テンプレート」でMarkdown本文を直接編集するか、`.md`をアップロードします。IDを変更して保存すると別テンプレートになります。文書種別、必須見出し、必須表の列を設定できます。個人テンプレートはこのPC内の書式候補として保存し、GitHubの共有状態へ一括送信・取り込みしません。

実際の生成には、「開発準備・書式登録」で選択し、リーダーの承認・マージを確認したプロジェクト書式を使います。登録するMarkdown・定義・対応表をGitHubのPRでレビューし、マージコミットとハッシュを固定します。参加した別PCでもGitHubの承認と内容を検証して専用キャッシュに保存するため、同名の個人書式を上書きしません。

個人テンプレートの編集で承認済みのプロジェクト書式は変わりません。共有書式を変えるときは新しい登録PRで再承認します。新しい文書種別を追加した場合も、その書式を登録してから開始します。

変数は `{{project.name}}`、`{{document.title}}`、`{{document.version}}`。AIは章構成を維持して生成し、必須項目を機械検証します。書式エラーがある文書は承認できません。生成に使用した本文とハッシュを成果物に保存し、テンプレート変更で既存成果物を変更しません。

## OSSライセンスの許可リスト

MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、0BSD、Zlib、BSL-1.0を初期ONで表示します。各候補と手入力の候補をチェックでON/OFFにできます。手入力はSPDX IDを使い、表示名も指定できます。OFFの候補も保存され、他PCへ共有します。設定の変更時は登録PRを作り直してマージを確認します。

必須skillが選定ルールと許可リストをAIへ渡します。GitHub Actionsは固定版のOSV-Scannerで依存関係を検査し、未許可・不明・対象なし・取得失敗を合格にしません。実際のマージ禁止には、GitHubのルールで画面に表示するOSSチェックを必須にしてください。GitHubトークンにはWorkflowsの書き込み権限も必要です。

v0.2.xから更新した既存プロジェクトも、開発前にOSS設定を含む登録PRの作成・マージ確認が必要です。手順と検査範囲は[OSSライセンス設定](docs/oss-license-policy.md)を参照してください。

## モデル・Skills・Tools

複数モデルをOpenAI互換API/Anthropic Messages形式で登録し、general・design・coding・reviewに割り当てられます。初期版のエージェントはタスクごとに1モデルで文書/コードを生成し、必要時に質問して停止します。文書の書式修正は1回試行します。

ponytailは `DietrichGebert/ponytail` のcommit `09c434ab73ca43761c5d8b0c5d341926c2fba710` を同梱しています。MITライセンスは同梱ディレクトリにあります。独自skillはブラウザへ本文を入力して追加・有効化できます。

Toolsは登録コマンドと、JSON応答形式のMCP Streamable HTTPの接続試験・手動tool呼出しに対応します。コマンドの例:

```json
["{python}", "-m", "unittest", "discover", "-s", "tests", "-v"]
```

`{python}` と `{git}` は環境設定のパスへ展開します。テスト実行時は「このPCでの登録コマンド実行を許可」を有効にして、対象タスクで手動実行します。検証タスクは、依存する実装タスクの承認済み成果物を検証用ディレクトリへ復元して読み取り・テストします。別PCで生成したソースも共有成果物から取得できます。

テスト結果は対象成果物のID・ハッシュと関連付けて記録します。コマンドごとの最新結果が成功し、現在の対象ハッシュと一致する必要があります。以前の成功で最新の失敗を隠したり、変更前の結果を流用したりしません。手動検証を採用するときは検証内容の記録が必要です。

## 開発・試験・exeビルド

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe launcher.py
.\.venv\Scripts\python.exe scripts/build.py
```

成果物は `dist/AIWorkspace/`。実接続試験は起動済みの指定LLMに接続します:

```powershell
.\.venv\Scripts\python.exe scripts/live_llm_smoke.py
.\.venv\Scripts\python.exe scripts/live_code_smoke.py
.\.venv\Scripts\python.exe scripts/exe_smoke.py
```

テスト用の草案とログは `.runtime/`、exe試験のデータは `.exe-user-*/` に保存されます。これらと資格情報はGit管理対象外です。

## 現時点の範囲と設計との差分

- UIはReactではなく同梱のJavaScriptで実装し、外部CDNを不要にしました。
- 作業はタスク別ローカルディレクトリで分離し、GitHub APIでcommit・ブランチ・PRを作成します。ローカルGit worktree方式と既存ソースツリーの自動checkoutは未実装です。既存の大規模リポジトリを自動探索・編集する用途は追加実装が必要です。
- エージェントは構造化出力でファイルを生成します。エージェントは作業ファイルの読取・検索を最大8ステップ自動実行できます。追加した外部toolの自律実行、MCP stdio/SSE専用サーバー、OSレベルの隔離ランナーは未実装です。コマンドは信頼できるコードに限り、ユーザーが手動で実行してください。
- GitHub Enterprise、Projects、CI保護ルールの完全な自動判定、署名付き配布、自動更新、DBの自動バックアップ/マイグレーションは未実装です。
- 対話・成果物・検証記録・プロジェクト設定は同期操作でGitHubに送ります。個人テンプレートは自動同期せず、選択してPRへ登録した書式だけを共有します。同じ共有レコードの競合を手動統合するUIは未実装です。
- 旧schema version 1の`shared.json`は読み取り専用で移行元として参照し、個人テンプレートを取り込みません。旧版と新版の同時利用は避けてください。旧作業ブランチに既に含まれている所有者ファイルは自動削除しません。移行時の手順は [共同作業と書式登録](docs/collaboration-formats.md) を参照してください。
- 実際の2台のPCと複数GitHubアカウントを用いた受入、実際の人間のリーダー承認は未実施です。自動試験では2つの独立DBとGitHub APIの模擬応答で検証します。

操作・移行の詳しい説明は [共同作業と書式登録](docs/collaboration-formats.md)、検証結果は [テスト報告](docs/test-report.md)、設計は [詳細設計](docs/detailed-design.md) を参照してください。実装範囲と実際に確認した範囲は、これらの文書で確認できます。
